### 问题 1：白字白底

**根因（两处，都读代码确认过）：**

1. **浅色主题：`--navy` 变成了近白色。** 旧样式把 `--navy` 当深色品牌色，在它上面写死白字。`theme.css:43` 把 `--navy` 指向了 `--me-rail`，而 `grok.css:21` 在浅色下把 `--me-rail` 设成 `#f7f7f7`，结果：

## 3. 方案

### 3.1 问题 1：字色

**推荐做法：令牌化清理，外加一个防回归脚本。**

1. **把 `--navy` 改回“永远是深色”。** 在 `theme.css` 里把 `--navy` 和 `--navy-2` 从 `var(--me-rail)` 改成新令牌 `--me-hero`（浅色主题 `#111418`，深色主题 `#0f0f0f`）。
   - 这样 `.overview-focus` 这类“深底白字”的设计在两个主题下都成立。
   - `--me-rail` 继续给侧栏用。
   - 这一行能修好绝大多数浅色下的白字白底。
2. **单独修 `.secondary-action`：** 在 `grok.css` 里改成 `background: transparent; color: var(--me-ink); border-color: var(--me-line-strong)`，浅色、深色都适用，然后删掉 `theme.css:263` 里多余的深色特例。
3. **单独修 `.universe-open:hover`：** 改成 `color: var(--me-ink)`。
4. **补齐深色清单：** 把上面漏掉的 `chat.css` 那 5 处，以及 `styles.css` 里其余写死的浅色背景，统一改成读令牌（`var(--me-surface)`、`var(--me-surface-2)`、`color-mix(...)` 等）。这样以后不用再维护“深色特例清单”。可以分两步：先改一眼能看到的（输入框、卡片、表单），再改冷门的。
5. **防回归：** 新增 `frontend/scripts/theme-contrast.test.mjs`（纯 Node，不引入 Playwright），并入 `npm run test:i18n`。
   - **检查 A：** 在 `styles.css` 和 `chat.css` 里，凡是 `background` 写死浅色的规则，只要同一条规则的 `color` 用的是会随主题变的令牌（`--ink`、`--me-ink`、`--c-ink`、`--navy`），就判失败。同样，凡是写死白字（`#fff` 等）的规则，如果背景用的是会变浅的令牌，也判失败。
   - **检查 B：** 解析 `theme.css` 和 `grok.css` 两个主题下的令牌值，对每一对“文字令牌/背景令牌”算 WCAG 对比度，正文要求至少 4.5，弱化文字要求至少 3。
6. **截图验收：** 用现有的 `run` 流程在 Mac 上开两个主题，截 9 张图：对话、公司总览、预测工作台、资料库、证据、技能、记忆、设置、新建 bot 弹窗。

**备选：** 全面改成只有深色主题（去掉浅色）。不推荐：设置页已经有“浅色 / 深色 / 跟随系统”的开关（`theme.mjs`），研究页面上的大段表格也更适合浅色。

**涉及文件：** `frontend/src/theme.css`、`grok.css`、`styles.css`、`chat.css`，新增 `frontend/scripts/theme-contrast.test.mjs`，`frontend/package.json`（把测试加进脚本）。

**数据模型：** 无。

**风险：** 改 `styles.css` 的范围大，可能让一些页面的颜色变平淡。缓解：一次提交一个页面，每次都截图对比。

### 3.2 问题 2：圆球头像，视线跟随

**推荐做法：自己画的 SVG 圆球，一个全局的鼠标监听驱动所有头像。**

- **造型：** 我们自己画，**不复制 xAI 或 Grok Bot 的商标素材**，只借“纯色圆球 + 两只竖椭圆眼睛 + 一点高光”的风格。
  - 圆：`<circle>` 加一个径向渐变做高光。
  - 眼睛：两个白色竖椭圆，里面的深色瞳孔是可以移动的 `<g>`。
  - 圆球的颜色默认接近 bot 的强调色，背景和文字对比度不低于 3。
- **组件：** 新建 `frontend/src/BotOrb.tsx`，提供 `<BotOrb color size track label />`。它替换 `BotAvatar`（`BotPages.tsx:42`）和对话页顶部那份内联头像（`AgentChatPanel.tsx:370`），并用在新建框的预览里。
- **视线跟随：** 新建 `frontend/src/gaze.mjs`，纯逻辑，可以单独测试。
  - 全页面只挂**一个** `pointermove` 监听，用 `requestAnimationFrame` 节流，把光标位置广播给已注册的头像。
  - 每个头像用 `getBoundingClientRect()` 算自己的中心，按角度把瞳孔偏移到 `min(距离 / k, 最大偏移)`，只改 `transform: translate()`，不触发重排。
  - 用 `IntersectionObserver` 跳过不在屏幕上的头像；页面 `visibilitychange` 隐藏时停止计算。
  - 光标停 3 秒以上，瞳孔慢慢回到中间；每 4 到 7 秒随机眨一次眼（`scaleY` 动画）。
  - 触屏没有光标，就看向最后一次点按的位置，然后回中。
- **无障碍：**
  - `prefers-reduced-motion: reduce` 时瞳孔固定居中、不眨眼（CSS 媒体查询加 JS 两边都判断）。
  - SVG 设 `aria-hidden`，外层元素带 `aria-label = bot 名`。
  - 侧栏头像很多时，只有当前 bot 和悬停的那一行跟随，其余静止。这一点可做成开关，见开放问题。
- **数据模型（MVP 不改表）：** 沿用 `Bot.avatar` 字符串，用约定前缀编码。
  - `orb:<颜色名>`（如 `orb:pink`，不超过 16 个字符）表示圆球。
  - 其他值照旧当 emoji 或文字显示，旧数据不受影响。
  - 服务端 `agent_bots.py` 的头像校验加一条：`orb:` 后面必须是调色板里的颜色名。
  - 调色板 11 色，对应截图里的：黑、棕、红、橙、黄、绿、青、蓝、紫、粉、灰，都定义成 CSS 令牌，深色主题下各提亮一档。

### 3.5 问题 5：每个 bot 接自己的 Telegram bot

**数据模型：新表 `agent_telegram_bots`**，取代 `agent_telegram_bind`：

| 列 | 说明 |
|---|---|
| `id` uuid PK | |
| `owner_hash` | 只属于这个 owner |
| `bot_id` uuid，指向 `agent_bots.id`，**唯一** | 对应哪个 app bot。默认 bot 那一行就是现在的共用 bot |
| `token_cipher` | `secret_box.encrypt_secret`，任何接口都不返回 |
| `token_fingerprint` | `sha256("tg-token:" + token)`，**唯一**，防止同一个 token 配给两个 bot（两个进程抢同一个 `getUpdates` 会报 409） |
| `tg_bot_id`、`bot_username` | 保存 token 时服务端调 `getMe` 拿到，用于校验和显示 |
| `chat_id`、`user_id` BIGINT | 绑定的 Telegram 账号 |
| `bind_code_hash`、`bind_code_expires_at` | **补上 30 分钟过期检查** |
| `update_offset` BIGINT | **持久化 offset**，重启不重放 |
| `status`、`last_error`（已脱敏）、`created_at`、`updated_at` | 设置页显示「运行中 / 未绑定 / token 失效 / 冲突」 |

- `agent_telegram_messages` 加一列 `telegram_bot_row_id`。Telegram 的 message id 只在一个 chat 里唯一，不同 Telegram bot 和你的私聊是不同的 chat，所以按回复找 bot 时必须在同一个 Telegram bot 范围内查。
- （第二期）新表 `agent_telegram_cards`：把 `pending_cards` 从内存挪进数据库，键是 `(telegram_bot_row_id, short_id)`，带过期时间。顺带解决“重启后按钮过期”。

**进程模型：推荐“一个进程，管多个 token”。**
- 仍是同一个 LaunchAgent `com.market-evidence-agent.telegram-bridge`，Mac 上不新增服务。
- 主循环每 30 秒从数据库对账一次 token 集合：新增的起一个 asyncio 轮询任务（每个 token 一个 `getUpdates` 长连接），删掉或换了 token 的取消对应任务，其余照旧。
- 每个轮询任务自带 offset（写回数据库）、自己的确认卡、自己的发件箱，只发出 `telegram_bot_row_id` 是自己的消息。
- 单实例锁：在 `data/` 下放一个文件锁，防止起两个桥接。收到 409 就标记成「冲突」，并在设置页提示。
- 一个 token 出错（401 等）只停那一个任务，标记成「token 失效」，不影响其他 bot。
- **备选 A：每个 bot 一个 LaunchAgent。** 不推荐：每建一个 bot 都要装一个 plist，删 bot 要卸载，`launchctl` 要权限，日志也分散，Mac 运维负担明显变重。
- **备选 B：Webhook。** 不可行：Mac 没有公网地址，而且 10-27 方案已定“不上云”。

**收发路由：**
- **收：** 哪个 token 收到的消息，就进哪个 app bot 的那条线，不用写 `@名字`。默认 bot 的 Telegram 保留现有的 `route()` 逻辑（按回复、`@名字`、默认），这样没配自己 token 的 bot 仍能经共用 bot 收发。
- **发：** `enqueue` 选通道的顺序：
  1. 这个 bot 有自己的、**已绑定**的 Telegram，就走它，消息开头不用再加 bot 名。
  2. 否则走默认 bot 的 Telegram，开头加「[bot 名]」，和现在一样。
- **确认卡：** 在哪个 Telegram bot 里出的卡，按钮就在那里，同意后执行在对应 app bot 的线里（卡片里已有 `bot_id`）。
- **只认主人：** 每个 Telegram bot 各自校验 `chat_id` / `user_id`。陌生账号和群聊照旧拒绝（`run_telegram_bridge.py:235-245`）。

**/bind 流程（bot 档案页里新增「Telegram」卡）：**
1. 在 BotFather 建一个 bot，把 token 贴进来。服务端调 `getMe` 校验，成功后只显示 `@用户名` 和 token 末 4 位，不回显 token。
2. 点「生成绑定码」，页面给出一个 `https://t.me/<用户名>?start=<码>` 按钮，手机上一点就能打开并发送 `/start <码>`。码 30 分钟过期，**这次真的检查**。
3. 桥接最多 30 秒内认到新 token，确认绑定。卡片变成「已绑定 · 运行中」，可以「解绑」或「换 token」。换 token 会清空绑定和 offset。
4. 设置页原来的 `TelegramBindCard` 改成总览：列出各 bot 的 Telegram 状态，默认 bot 那一行就是原来的共用 bot。

注意：Telegram 规定 bot 不能先给用户发消息，**每个 Telegram bot 都要你自己点一次 /start**，所以“每个 bot 单独绑定一次”省不掉。

**接口：** 在 `/agent-chat/bots/{id}/telegram` 下提供 `GET` 状态、`POST token`、`POST bind`、`POST unbind`、`DELETE`（删掉 token）。原来的 `/agent-chat/telegram/*` 保留一个版本，作为默认 bot 的别名，之后删除。

**迁移：**
- 启动时一次性把 `agent_telegram_bind` 里那一行搬进 `agent_telegram_bots`，`bot_id` 设为 `ensure_default_bot` 的 id，token 密文原样复制（同一个 key，不用重新加密），`chat_id` 等也照搬。
- 旧的 `agent_telegram_messages` 一律归到默认 bot 那一行。
- 迁移脚本可以重复执行，留旧表一个版本当回滚。
- **对 Levi 无感：** 现有的 Telegram bot 照常工作，只是挂在了「助理」名下。

**安全：**
- token 用 `secret_box` 加密存储，不进日志（把 `_redact` 扩展成按所有已知 token 的指纹打码），不回给浏览器，只返回用户名和末 4 位。
- 删除 app bot 时同时删掉它的 token 行，并提示“去 BotFather 撤销 token”。
- 每个 Telegram bot 的每日上限沿用 `bot.daily_notify_cap`。

**Mac 运维影响：**
- 不加新的 LaunchAgent，部署后重启一次桥接即可。
- N 个 token 就是 N 条长连接，20 个以内可以忽略。
- 新增日志字段 `telegram_bot=@username`，不含 token。
- `live_check_telegram.py` 改成多 token 版。

**涉及文件：**
- 修改：`app/agent_chat_models.py`、`app/agent_telegram.py`（几乎所有函数都要加 `bot_id` / row 参数）、`app/agent_chat_stream.py`（旧接口改成别名）、`app/agent_bots_api.py`（新接口）、`app/agent_bots.py`（删除 bot 时联动）、`scripts/run_telegram_bridge.py`（拆成主循环加每个 token 的任务）、`scripts/live_check_telegram.py`、`frontend/src/BotPages.tsx`、`AgentChatPanel.tsx`（设置页总览）、`frontend/src/api.ts`
- 测试：`tests/test_telegram_*.py`、`test_agent_notify.py`，新增 `test_telegram_multi_bot.py`

**风险：**
- 桥接是这几天修得最多的地方（同意卡按钮、过期），重构容易回归。缓解：
  - 先把“每个 token 一个任务”做成纯重构（只有一个 token 时行为完全不变），跑全部 Telegram 测试加 live check。
  - 再加多 token。
  - 安排在第 4 节的最后一步。
