# App-wide Chinese and English display design

## Status

- Design scope approved in conversation on 2026-09-28.
- Written spec records the approved scope and serves as the implementation reference.
- No product code or persisted application data has been changed for this feature.

## Goal

Let a user switch the Market Evidence Agent workspace between Chinese and English from the top bar beside the stock selector. The choice applies across all seven workspace sections and remains selected after a page reload. English mode also makes previously saved DeepSeek material analyses and research briefs readable in English.

The language is a presentation preference. It must not change source records, prediction inputs, probabilities, forecast versions, evidence selection, or Jev calls.

## User-visible behavior

1. Add a clearly labelled `中文 / English` selector beside the stock selector.
2. Keep Chinese as the default so existing users see the current language on first use. Persist the selected locale in `localStorage` and apply it immediately without a page reload.
3. Translate all user-facing interface copy in overview, forecast, evidence, materials, revisions, evaluation, historical replay, shared navigation, loading/empty/error states, dialogs, controls, chart labels, accessibility labels, and action results.
4. Use locale-aware date, time, and number formatting. Keep ticker symbols, API codes, model names, numerical values, and URLs unchanged.
5. Preserve source-authored filing titles and exact SEC/source quotations in their original language. They remain linked to the same original sources.
6. In English mode, display saved AI narrative fields from both material-analysis versions and forecast research briefs in English. This includes summaries, facts, supporting and counter reasoning, uncertainties, brief findings/background/conflicts/open questions/change descriptions, material key-number labels and periods, and input-quality explanations. Citation IDs, source IDs, fixed enum values, dates, source titles, and verbatim quotes remain unchanged. Translate any descriptive words around a key number only if every numeric token and its value remain identical.
7. Generate a translation only when English display first needs that record. Reuse the saved translation on later visits. Display an English loading status while a translation is being prepared. If translation fails, keep the interface in English, show a clear English fallback notice, and identify the accompanying source text as the original language; never imply that it was translated.

## Recommended architecture

### Frontend locale layer

- Introduce a small typed locale context/provider at the application root, with `zh-CN` and `en-US` locales.
- Keep UI phrases in locale dictionaries with stable keys. Components use a translation helper rather than embedding locale conditions or sending UI copy to an AI model.
- Add shared locale-aware date/number formatters and translated labels for known API states/codes. Preserve safe unknown API codes verbatim with a localized generic explanation.
- Pass the locale through all workspace components, including nested material-analysis and research-brief views. Changing the locale rerenders the current route and does not refetch unrelated prediction data.

### Saved AI content translations

- Keep original material-analysis payloads and immutable forecast-version research briefs as the canonical records.
- Store translations in a separate `ai_content_translations` table, rather than editing canonical JSONB records. Each entry is keyed by content kind, immutable record ID, canonical source-content SHA-256, locale, and translation prompt version. Store only translated display fields plus provider/model metadata and creation time.
- Add explicit backend localization operations for a material-analysis version and a forecast-version brief. An operation returns a matching cached translation when present; otherwise it translates the approved narrative fields using the existing configured DeepSeek provider, validates the translated shape against the source structure, and saves the cache entry.
- Preserve exact identifiers and citation references by translating only approved narrative values. Source quote strings, source titles/URLs, dates, enums, probabilities, and numeric values are copied from the canonical source rather than regenerated by the translation model. The only exception is translating prose attached to a material key number, while retaining the exact numeric tokens and values.
- Use a unique database constraint and transaction-safe upsert/lock so concurrent requests for the same content do not create duplicate translations. A changed source hash naturally requires a fresh translation; an existing immutable record's cache remains stable.
- Translation is display-only: it is never fed into Jev, research-brief validation, evidence matching, or future prediction inputs. It does not create a forecast revision or mutate historical records.
- Translate lazily to control API usage. A failed provider call or invalid translation is not cached. The client can retry by requesting the same localization again.

## Data and API boundaries

- New persistent table creation follows the repository's explicit migration pattern and is additive. The server should return a clear migration-required error if the table is unavailable.
- Localization requests must identify the immutable material-analysis or forecast-version record; they must not accept arbitrary source text from the browser.
- Keep SEC/source text and its original URL outside the translation request except for the exact quote fields needed to enforce preservation. The translation request contains only persisted AI narrative fields and minimal context necessary to translate them.
- Existing Chinese analyses and briefs remain byte-for-byte unchanged. Translation metadata does not enter input fingerprints, prediction hashes, source manifests, or model-version records.

## Error handling and accessibility

- All progress, failure, retry, and fallback messages follow the selected interface locale.
- A translation request failure leaves navigation and all non-AI parts of the page usable. The affected AI content shows the original-language notice and a retry action.
- The language selector has a visible label, keyboard operation, and an accessible name in the active locale. Language changes announce that the display language changed without unexpectedly moving focus.

## Verification criteria

1. A first visit defaults to Chinese; switching to English updates the current page immediately, and reload restores English.
2. Every route and shared surface renders English labels, status text, errors, date/time, and numeric formatting in English mode, with no leftover Chinese UI strings in the covered workspace.
3. English mode translates an old material analysis and an old historical/live research brief; citations still point to the same source records, and all exact quote strings and source titles are unchanged.
4. Requesting the same translation again is a cache hit with no second DeepSeek translation call. A different source hash produces a new cache entry.
5. A provider failure or malformed translation displays a truthful English fallback and can be retried; it does not damage or replace canonical records.
6. Language changes do not create forecasts/revisions, alter Jev probabilities, change prediction inputs, or modify source data.
7. The existing Chinese workflow remains readable and usable. Frontend build, relevant backend tests, and route-level browser checks pass.

## Out of scope

- Translating the underlying SEC filing, media article, exact source quotations, or original source title.
- Changing any DeepSeek analysis, Jev prompt, forecast probability, model, source-selection rule, or prediction workflow because of the selected display language.
- Translating arbitrary user-uploaded document contents that are not saved AI narrative fields.
- Retrofitting translations into the canonical prediction records or rewriting historical data in place.
