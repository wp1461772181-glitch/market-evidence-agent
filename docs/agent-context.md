# 对话上下文管理

一轮对话发给模型的"更早的对话"由三层组成，共用一个预算。历史只投影完整用户问题和最终回答；旧工具批次、引用全文、审计与流程图不再重放或计量。短对话仍按同一问题和回答文本送出。

## 三层

| 层 | 内容 | 默认预算（64 KB 档） | 规则 |
| --- | --- | --- | --- |
| 层 1 | 最新的完整轮次，原文 | 32 KB | 只保留用户问题和最终回答；可见引用标记不变 |
| 层 2 | 层 1 之前、尚未进摘要的轮次，半压 | 24 KB | 用户原话最多 1000 字；答复只留开头 160 字；相关引用目录项也计入预算 |
| 层 3 | 更早的轮次，追加式分段摘要 | 8 KB（最近 ≤ 5 段） | 一条标注"记忆，不是证据"的注记，**挂在当前用户消息之后** |

拼装顺序：系统提示 → 层 2 → 层 1 → 当前用户消息 → 层 3 摘要 → 引用目录。失败、取消或未完成的轮次不进任何一层。每条目录标明回答开头和 `answers_back`，只列回答中出现过的编号；不包含引文、URL 或哈希全文。目录是系统写的定位提示，不是证据或用户原话。

**层 3 为什么在最后而不是最前面**：请求开头是模型服务商做前缀缓存的地方。摘要放在当前问题之后，使 `系统提示 + 层 2 + 层 1` 保持稳定。摘要和引用目录都用 user 角色，内容明确说明由系统写入，不是用户的话。

代码：`app/agent_context.py`（预算、渲染、选择，纯函数；`layer_rows` 就是一轮实际运行的规则）、`app/agent_chat_store.py`（`conversation_context` 读库）、`app/agent_context_summary.py`（摘要任务）、`app/agent_chat_stream.py`（拼进请求）。

## 预算从哪来

预算不是拍出来的常数，是从模型窗口倒推的（`derive_history_budget`）：

```
可用 = min( 窗口 − 固定开销, 想留的轮数 N × (单轮输入 X + 输出 Y) ) × 每个 token 的字节数
```

固定开销 = 系统提示 + 工具定义 + 本轮证据；默认窗口 128k、N=8、X=8000、Y=2000。两侧取小的那个：窗口大时不浪费，窗口小时自动收紧。换模型只改一个配置：

| 旋钮 | 作用 |
| --- | --- |
| `AGENT_MODEL_CONTEXT_WINDOW` | 模型窗口（token），默认 128000 |
| `AGENT_CONTEXT_BUDGET_KB` | 历史预算（KB），默认 64，**只能往下调**，上限是窗口算出来的那个数，下限 16 |

由同一个预算派生的闸：

| 闸 | 取值 |
| --- | --- |
| 历史预算 | 旋钮 |
| 入口保护（`agent_chat_stream.py` 返回 413） | 2 × 旋钮 |
| 工作流内的请求保护（`direct.Turn.model`） | 4 × 旋钮（本轮自己的工具结果另算） |
| 阶段读历史的文字视图 | 旋钮（`bounded_history`，不再是另一个 64000） |

启动时 `startup_self_check()` 会核对一遍：连一轮都装不下的配置直接报错，而不是等到请求进来才发现。

三层怎么分：层 1 拿一半，层 2 拿 3/8，剩下的给层 3。第 1、2 层按实际发送的问答字节与可见引用目录计量；目录项另预留 20 字节余量。64 KiB 总预算和 32/24/8 KiB 分配保持不变。

## 摘要（层 3）

- 一轮成功结束后，如果有轮次已经掉出层 1 和层 2 且尚无摘要，且待压内容 ≥ 2,000 字节，后台起一个任务（每个对话同时一个）。
- 用这次请求带来的模型和 key；key 只在任务内存里存活（超时 40 秒），不落库、不进日志。失败只记一行，下一轮重来。每生成一段摘要多一次模型调用，计在这次请求所用的 key 上；对话没有长到需要摘要时不会有这次调用。
- 输出严格 JSON `{"summary": "..."}`，≤ 400 字；服务端检查它没有写出被摘要轮次里没有的公司或数字（公司逐个核对，不设上限；把"下午三点"写成"15:00"这类时刻写法不算新数字），否则整段不用，下一轮再试。
- 一段一行，只追加，不回炉重压；最近 5 段之外的更早段落不再注入（有视野，不是无限记忆）。
- 摘要是记忆不是证据：不进"可信上下文"，也不参与实体/期间的可信来源拼装（`conversation_messages` 会把这条注记摘掉），回答的系统提示写明不能引用它。

## 检索侧的 Query 扩写

知识检索会先用模型把同一个问题写成最多 3 条检索说法（`app/knowledge/query_understanding.py`），查完即弃，索引里仍然只有一份原文。变体不许引入原问题没有的股票代码、数字或年份，否则整条丢弃；原始问法永远第一个查。没有模型可用时退化成规则表（`expanded_queries`），那是兜底，不是机制。精确来源读取（给了 `source_id`）不扩写。

## 哪个阶段读历史

当前流程先独立解析指代，再独立分类；无历史、结果集或待处理卡片的首个独立问题跳过指代解析。两个阶段收到既有三层上下文的文字视图，按完整消息保留到历史预算为止，避免把 JSON 从中间切断。

指代解析只把用户原话和服务器返回的对象范围作为补全依据；助手文字和摘要不能新增公司、数字、URL、来源 ID 或写授权。分类提供四类结果及结构化检索约束。回答模型只读取本轮接受的证据、当前原生工具协议、操作状态及服务器结果目录；以前的对话不作为事实证据。需要旧来源时可调用只读工具 `read_history_citation(turn_id, ordinal)`。服务端只接受当前目录中的句柄，从原始回答 manifest 读取快照并重新核验来源完整性、有效性与权限。成功来源会在本轮重新编号，回答必须使用新编号；重复读取复用该编号。失效、损坏或无原文时不以最新内容替代。目录覆盖层 1、层 2 中的完整回答，不包括摘要覆盖的轮次。派生（计算）引用不能直接读取，目录会提示先读父来源再重算。旧记录已被降级为 unavailable 且原文丢失时不可恢复。

时间/数量型 `refinement` 追问继承前轮任务范围；指代与分类的结构化范围冲突时先请求澄清。数字回答被证据闸拒绝后，允许在剩余预算内用相同证据无工具重写一次；被拒草稿只是数据，不是用户指令或写权限，重写仍需通过原护栏。

## 用量显示

输入框里模型选择器旁的"上下文剩余 xx%"，点击看各部分（系统提示、工具定义、早前摘要、半压历史、近期原文、剩余空间）。数据来自只读接口 `GET /agent-chat/conversations/{id}/context`（新对话为 `GET /agent-chat/context`），与真实拼装同一个函数，不调模型。"剩余"是本产品的预算，不是模型窗口；token 按 **字节 ÷ 3** 估算（中文一个字的 UTF-8 是 3 字节、约 1 token，按 ÷4 是英文口径，会低估四分之一）。

## 评测

`scripts/eval_context_retention.py` 用构造的长研究对话比较"现状窗口 / 同预算纯滑窗 / 分层"；分层评测按问答投影和目录组装，报告见 `docs/context-retention-report.md`。评测数字只代表构造对话，不代表线上提升。字节预算降低不代表 token 或延迟降低；不承诺固定降幅。
