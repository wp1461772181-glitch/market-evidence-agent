# 全量 SEC 申报重构方案（v1）

> 目标：把"抓下来就砍到 8 万字"改成"全文存下来、按章节切进知识库"。AI 分析这一环本轮不动，仍由用户手动触发。

---

## 一、一句话说清问题

现在的流程，抓取、分析、向量库三条下游全都建立在同一份**被砍到 8 万字**的文本上。

```
抓 SEC 原文（2.7 MB HTML）
   │
   ├─ 只留前 80,000 字符 ──→ 存数据库 content_excerpt（varchar(80000)）
   │                              │
   │                              ├─→ 分析只读前 24,000 字符（占 10-K 的 6.6%）
   │                              ├─→ 对话只取 3,000 字节
   │                              └─→ 切块嵌入 = 向量库（也止于第 80,000 字符）
   │
   └─ 其余 78% 直接丢弃
```

三个后果：

| 后果 | 实测数据 |
|---|---|
| 10-K / 10-Q 几乎全部被截断 | 73 份 10-K 中 72 份截断；213 份 10-Q 中 200 份截断 |
| 向量库只覆盖前 22% 正文 | 272 份文档的分块最大偏移精确等于 80,000 |
| 文本被 XBRL 标签污染 | 343 份文档、1,679 个分块里含 `us-gaap:` / `ix:nonfraction` 之类的标签碎片 |

财报最值钱的部分（财务报表与附注，Item 8）通常在正文 20 万字符之后，按位置截断等于永远读不到。

---

## 二、改完之后的形态

```
抓 SEC 原文（HTML，2.7 MB）
   │
   ├─→ 解析成纯文本（无字数上限）
   │      │
   │      ├─ content_text（全文，TEXT）──→ 按章节切块 → 嵌入 → 向量库 ★本次
   │      │
   │      └─ content_excerpt（前 8 万字，保留）──→ 分析 / 界面（行为不变）
   │
   └─ 原始 HTML 不入库（省 ~1 GB）
```

前后对照：

| 维度 | 现在 | 改后 |
|---|---|---|
| 库里存的正文 | 前 8 万字符（varchar 定长） | 全文（TEXT） |
| 全库文本量 | 2,542 万字符 | 约 7,100 万字符（约 71 MB） |
| 向量库分块 | 12,946 块，覆盖前 22% | 约 36,000 块，覆盖全文 |
| 分块边界 | 按句子硬切，可能落在章节中间 | 按 Item / 附注章节对齐 |
| 表单支持 | 只有 10-K / 10-Q / 8-K（数据库有硬约束） | 加 DEF 14A、20-F、40-F |
| 分析读多少 | 前 24,000 字符 | **不变**（本轮不做） |

## 三、五个步骤

### 第 1 步：数据库增加"全文"两列，放开表单范围

**做什么**

- `sec_filing_inventory` 增加 `content_text`（TEXT，全文纯文本）、`content_text_sha256`（全文指纹）、`content_length`（字符数）。
- 保留 `content_excerpt`（前 8 万字）**语义完全不变**——分析和界面还在用它，这样本轮零回归。
- 表单范围从 3 种扩到 6 种：`10-K / 10-Q / 8-K / DEF 14A / 20-F / 40-F`。
- 同步放开数据库硬约束 `ck_sec_filing_inventory_form`（现在是 `CHECK form IN ('10-K','10-Q','8-K')`，不改约束插不进去）。

**为什么扩这几种**

- `DEF 14A`：股东会委托书，含高管薪酬、股权激励、董事会构成——对"公司治理/激励"类分析有独立价值。
- `20-F / 40-F`：外国发行人年报（如台积电、阿斯麦），现在完全抓不到。
- **不抓** Form 3/4/5（内部人交易）与 144（减持）：单公司十年上千份、信息密度极低，会把库撑大十倍而无分析价值。

**改哪里**

- `app/models.py`：`SecFilingInventory` 加列。
- `app/sec_filings.py:43` `SUPPORTED_FORMS` 与 `:707` 的表单过滤同步。
- 新增 `scripts/migrate_filing_fulltext.py`（仓库没有 alembic，沿用现有 `scripts/migrate_*.py` 手写 DDL 的做法；`Base.metadata.create_all` 不会改已存在的列类型）。

**怎么算做完**：迁移脚本在线上库跑通，插入一条 DEF 14A 测试行不报错，`content_text` 能存 36 万字符。

---

### 第 2 步：写全量抓取

**做什么**

- 抓取器返回全文（不是返回前 8 万字），保留 50 MB 单文档上限作为防护。
- 新增批量脚本 `scripts/backfill_filing_fulltext.py`：
  - 支持 `--symbol` / `--all` / `--forms` / `--limit`；
  - 断点续抓：`content_text IS NULL` 的就是待办，中断后重跑自动继续；
  - 失败重试 3 次并记录原因，不因一份失败中断整批；
  - 复用现有的限速器（`MIN_REQUEST_INTERVAL_SECONDS = 0.2`，即最多 5 次/秒，SEC 官方上限 10 次/秒）。
- 8-K 仍然优先取同一 accession 下的 Exhibit 99.1（业绩公告正文）。

**为什么原始 HTML 不入库**：697 份要占约 1 GB；只存纯文本约 71 MB。代价是"将来想改进 HTML 解析就得重抓"——但重抓只要几分钟，不值当为此多存 1 GB。

**改哪里**

- `app/sec_filings.py`：`fetch_inventory_content` 拆出"取全文"与"生成 8 万字摘要"两个动作。
- 新增 `scripts/backfill_filing_fulltext.py`。

**怎么算做完**：全库 10-K / 10-Q 抓完，抽查 AVGO 10-K 的 `content_text` 长度 = 365,785 字符（含 Item 8 财务报表与附注）。

---

### 第 3 步：切块器按章节切（v4）

**做什么**

- 先按标题把文档切成"章节"（`Item 7. MD&A`、`Item 8. Financial Statements`、`Note 12 — Debt` 这类），再在章节内按 512 token 切块，相邻块重叠 64 token。
- 超长表格按"行"切，每行独立成块并带上表头与所在章节，不再丢进 `needs_review`。
- 切块版本号 `CHUNKER_VERSION` 从 `markdown-sentence-v3` 升到 `v4`。

**为什么升版本号就能一键换血**

索引的"代际"（generation）由 `嵌入模型 + 嵌入格式 + 切块器版本` 共同算出（`app/knowledge/settings.py:34`）。版本号一变就是新一代，检索只认当前代：

- 新块在后台慢慢建，建好前不影响使用；
- 用户不会看到"半新半旧的检索结果"；
- **要回滚，只需把版本号改回 v3**，旧块原封不动还在库里。

**顺带修的两个老毛病**

1. 343 份文档里的 XBRL 标签垃圾：重抓全文后自然消失。
2. 211 个 `needs_review` 分块黑洞：现在这些块**永远不可检索**，改成超长继续拆，不再丢弃。

**改哪里**

- `app/knowledge/chunking.py`：章节识别 + 切分策略。
- `app/knowledge/sources.py:75`：索引源文本从 `content_excerpt` 换成 `content_text`（没有全文时回落到 excerpt，保证过渡期可用）。
- `tests/test_sec_filings.py`：现有断言大量依赖"截断到 80,000"，需要按新语义更新。

**怎么算做完**：AVGO 10-K 切出约 178 块（按 512 token/块），且块 146～178 落在 Item 8 财务报表区。

---

### 第 4 步：夜里重建索引

**做什么**

- 一次性脚本，**不在 API 进程里跑**（避免和线上请求抢 CPU）。
- 建完约 36,000 块的嵌入。

**为什么可以慢慢来**：检索在切代际前一直用旧索引，用户无感；切代际是瞬间的。

**改哪里**：新增 `scripts/rebuild_knowledge_index.py`（复用现有 `ingest_documents` 与索引任务队列）。

**怎么算做完**：库里当前代际的 ready 块数达到 3 万以上，`pending` 清到 0。

---

### 第 5 步：验收（四条硬指标）

| # | 验收项 | 现在 | 改后必须 |
|---|---|---|---|
| 1 | 检索 AVGO 10-K 的 `CONSOLIDATED BALANCE SHEET` | 命中失败 | 命中，且引注偏移 > 200,000 |
| 2 | 含 `us-gaap:` / `ix:nonfraction` 的分块数 | 1,679 | **0** |
| 3 | 10-K / 10-Q 里 `content_truncated = true` 的比例 | 94%~99% | **0**（存全文不再截断） |
| 4 | 知识库覆盖率 | 7764 完成 / 23006 排队 | ready 块 ≥ 3 万，排队 = 0 |

第 1 条现在必然失败，改完必须通过——它就是这次重构的意义所在。

## 四、时间、资源、钱

| 环节 | 规模 | 花钱 | 耗时 |
|---|---|---|---|
| 抓取 SEC 全文 | ~1,200 次请求（697 份主文档 + 附件） | **$0**（SEC 免费） | 约 4~5 分钟（5 次/秒） |
| 下载体积 | ~1 GB HTML，解析后丢弃 | $0 | 同上 |
| 入库文本 | 约 71 MB | $0 | 同上 |
| 切分 + 嵌入 | 约 36,000 块，本地 BGE-M3（CPU） | **$0** | 约 10 小时（实测 2,300~3,200 块/小时） |
| AI 分析 | **本轮不做** | — | — |

**结论**：这是一次纯工程投入，几乎不花钱，花的是编码时间 + 一个晚上跑索引。

## 五、风险与回滚

| 风险 | 应对 |
|---|---|
| 新检索效果不如旧 | 新旧代际并存，回滚只需改版本号，数据不用重建 |
| Postgres 大字段拖慢列表接口 | 列表查询必须按列取，禁止 `SELECT *`（需要复核所有列表接口） |
| 重建抢 CPU 影响线上 | 独立进程 + 限流，放夜里 |
| SEC 返回 403 / 429 | 已有 User-Agent + 0.2 秒间隔；失败重试 3 次 + 断点续抓 |
| 表单扩展导致行数暴涨 | 只加 3 种低频表单；Form 3/4/5、144 明确排除 |

## 六、本轮明确不做

1. **不动分析窗口**：分析仍读 `content_excerpt` 的前 24,000 字符。这是已知局限，属于第二阶段（章节选择式读取 / XBRL 结构化数字）。
2. **不做全文 map-reduce 分析**。
3. **不重跑 603 份历史 AI 分析**：它们基于截断文本生成，标为旧代，等用户手动重跑。
4. **不改前端页面结构**：只把"已抓取字符数 / 是否截断"显示准确。
5. **不删历史数据**：清正文而不删行（预测版本的证据清单靠 `accession_number` 定位，删行会让历史引注指向空）。

### v6 修了什么（全量 93 份实测）

| 表单 | 份数 | 分块 | 覆盖率 | 丢字 | 丢锚点 | 错标章节 |
|---|---|---|---|---|---|---|
| 10-K | 6 | 1,432 | 99.91% | 0 | 0 | 0 |
| 10-Q | 15 | 1,787 | 99.92% | 0 | 0 | 0 |
| 8-K | 67 | 577 | 99.79% | 0 | 0 | 0 |
| DEF 14A | 5 | 886 | 99.96% | 0 | 0 | 0 |

改造前：最差一份 90.9%，META 10-K 的 `CONSOLIDATED BALANCE SHEET` 标题掉进空洞，552 块（11.6%）标着不属于它的章节。

三条根因与对策：
1. `flush()` 判定为页眉页码就**直接丢弃** → 改为进 `pending` 缓冲挂到下一块之前（攒够 200 字符才单独成块）。
2. 标题行被消费后文字**不进任何块** → 同上，字符随下一块入库。
3. 全大写标题规则太松（`EVP & CFO`、`Amazon.Com, Inc.`、`SECURITIES AND EXCHANGE COMMISSION` 都成了章节名）→ 要求上下空行、无数字、词数 2–10、缩写占比 < 60%、黑名单、拒绝注册人名；`Item 9.01` 的细空格 U+2009 归一化。

注意一个已修的自造 bug：第一版直接拿 `pending` 起点当块起点，produced 出 `start > end` 的倒置区间（10-Q 覆盖率反而掉到 87.6%）。现在只有"紧邻且中间无文字"的片段才能当前缀，否则先 `_emit_pending()` 单独成块。
